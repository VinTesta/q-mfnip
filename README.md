# q-mfnip

Code, data and paper for a study of quantum minimum finding applied to the maximum flow network interdiction problem (MFNIP). The study uses the Dürr–Høyer algorithm (Grover-based minimum finding) on the cardinality-constrained variant of the problem, in which up to k arcs of unit cost may be removed. One qubit represents each arc. A Dicke-state preparation produces the uniform superposition over the feasible interdiction plans F_k = {x : |x| <= k}, which enforces the budget. A threshold oracle marks the plans whose residual maximum flow is below the current threshold. The repository contains a query-level simulation of the search compared with classical search over the same space, qubit and gate counts of the state preparation and of two oracle realizations, a small Grover demonstration on IBM hardware (m = 3 arcs, k = 1), and a MILP formulation used as the reference optimum and as the practical classical baseline.

The markdown cells of the notebooks, `docs/protocolo.md` and `docs/resultados-entrega2.md` are written in Portuguese. Code, column names, `docs/literature-search.md` and the paper are in English.

The protocol and the results file number the two hypotheses H4 and H5, following an earlier version of the project. The paper calls them H1 (scaling in simulation) and H2 (hardware).

## Repository layout

```
src/qmfnip/
  instances.py         network instances (random and layered families), scenarios, max flow, full-cut cost
  solvers/base.py      solver interface and registry
  solvers/exact.py     MILP (HiGHS through SciPy) and brute-force reference solvers
  solvers/search.py    Dürr–Høyer (query-level simulation) and classical random-order search as solvers
  grover.py            feasible search space F_k, query-level Grover/BBHT sampler, Dürr–Høyer, classical search
  oracle.py            Qiskit circuits: Dicke-state preparation, truth-table phase oracle, arithmetic oracle,
                       resource counting, sampling on simulators and IBM backends (free plan only)
  playground.py        experiment runner with incremental recording and resume
  evaluation.py        per-run evaluation, summaries, scaling-exponent fits
  outputs.py           experiment folders under outputs/, environment capture, LaTeX tables
  plots.py             figures
tests/                 pytest suite
notebooks/             00 to 05, see below
outputs/               recorded experiment data, one folder per experiment
paper/                 English manuscript: main_en.tex, main_en.pdf, sections_en/, tables_en/, tables/, figures/,
                       macros.tex, references.bib
docs/protocolo.md            experimental protocol (hypotheses, parameters, instances, metrics), frozen before E1
docs/resultados-entrega2.md  every number cited in the paper with the file it comes from (generated by notebook 05)
docs/literature-search.md    exact queries of the systematic search for prior work cited in Section III-E of the paper
```

## Setup

Requires Python 3.11 or later and [uv](https://docs.astral.sh/uv/). The recorded experiments used Python 3.14.4; exact package versions are pinned in `uv.lock` and recorded in each experiment's `environment.json`.

```
uv sync --all-extras
```

This installs the base dependencies (numpy, scipy, pandas, matplotlib, psutil) and the two optional groups defined in `pyproject.toml`:

- `quantum`: qiskit, qiskit-aer, qiskit-ibm-runtime (needed by `oracle.py`, notebooks 03 and 04, and part of the tests);
- `dev`: pytest, ruff, jupyterlab, ipykernel, nbconvert, nbformat, nbstripout.

The groups can also be selected individually with `uv sync --extra quantum --extra dev`.

## Tests

```
uv run pytest -q
```

The tests include the validation of the MILP against brute force, of the query-level Grover sampler against a full state-vector simulation, and of the Qiskit Grover circuit and Dicke preparation against the query-level model on small instances.

## Notebooks

Start Jupyter with `uv run jupyter lab`, or execute a notebook without opening it:

```
uv run jupyter nbconvert --to notebook --execute notebooks/02_durr_hoyer_scaling.ipynb --output-dir /tmp
```

Each notebook has three sections: constants and instances, execution, evaluation. Results are written to a new folder under `outputs/` named `<timestamp>__<solvers>__<family>__n<min>-<max>__runs<repetitions>`.

| Notebook | Experiment | What it produces |
|---|---|---|
| `00_playground` | none (configurable sandbox) | Runs any set of registered solvers on the same instances and compares them with the MILP reference. |
| `01_milp_scaling` | MILP scaling study | Largest instance size for which the MILP proves optimality within the time limit (random and layered families, budgets of 25, 50 and 75% of the full-cut cost, 3 seeds, 20 s). Compares with the earlier benchmark in `outputs/legacy/bench_milp_v2/`. |
| `02_durr_hoyer_scaling` | E1 (hypothesis H4) | Cost (oracle queries plus classical evaluations) until the optimum is measured, for Dürr–Høyer, classical search in random order and exhaustive enumeration over F_k; 30 layered unit-cost instances, 200 runs per solver and instance; fitted scaling exponents with bootstrap intervals. Reuses the stored folder if it is complete. |
| `03_oracle_resources` | E2 | Qubits, two-qubit gates and depth of the Dicke preparation, the truth-table oracle and the arithmetic oracle, as logical circuits and transpiled to the `FakeFez` noise model. |
| `04_ibm_demo` | E3 (hypothesis H5) | Grover amplification for one instance with m = 3 and k = 1 on the ideal simulator, on `FakeFez` and on IBM hardware, for two variants: Dicke preparation over F_1 (N = 4) and uniform preparation over the hypercube (N = 8). Binomial test of the frequency of the optimal plan against 1/N. |
| `05_article_figures` | E4 and E5 | Reads the folders in `outputs/` (no heavy computation) and writes the figures in `paper/figures/`, the tables in `paper/tables/` and `docs/resultados-entrega2.md`. |

Notebook 04 submits to IBM hardware only when `ALLOW_HARDWARE = True` and an IBM Quantum account is saved locally, for example with `QiskitRuntimeService.save_account(channel="ibm_quantum_platform", token=..., set_as_default=True)`; the token never goes into the notebook. Hardware access is restricted to free-plan (Open Plan) instances: `free_plan_backend` selects the free instance of the account and `sample_circuits` refuses to submit through a paid one. With the default `REUSE_EXISTING = True`, the notebook reuses the stored E3 folder, including `counts_ibm.csv`, without submitting a new job. A stored job can be fetched again by setting `RECOVER_JOB_ID`.

The hardware run in this repository is IBM job `dbmujid8mdtc73d8m2h0` on `ibm_fez` (4096 shots per circuit, submitted 2026-11-06).

Each experiment folder contains `manifest.json` (configuration, solvers, instance content hashes), `environment.json` (Python and package versions, CPU, operating system and git state at run time), `instances/` (the instances as JSON), `runs/` (per-run records) and the summary tables and figures written by the notebook. The git commit recorded in `environment.json` refers to the development repository, not to this one.
